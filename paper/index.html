Benchmarking open-source tools for estimating urban transport flows: walking, cycling and driving

Author

Robin Lovelace

Published

August 7, 2026

Introduction

Urban transport planners increasingly rely on open-source tools to estimate pedestrian, cycle and motor traffic flows on street networks. The tools benchmarked here — cityseer (Simons 2022), madina (Sevtsuk and Alhassan 2025), sDNA (Cooper and Chiaradia 2020), flownet (Krantz, Dünch, et al. 2024) and aequilibrae (Camargo 2024) — span very different modelling traditions: network centrality and space syntax, gravity and floating-catchment-area demand models, path-sized logit assignment and user-equilibrium traffic assignment. Yet no systematic benchmark has compared these tools against the same observed counts, on the same networks, with the same demand inputs, so evidence-based tool choice remains difficult.

A structural gap motivates this work: most tools belong to the all-or-nothing (AoN) shortest-path family, which assigns each origin–destination pair to a single deterministic route. Only a few implement dispersed or multi-path assignment, spreading flow across several plausible routes via stochastic user equilibrium (SUE), user equilibrium (UE) or path-sized logit (PSL) models. Whether the route-choice model class materially affects predictive performance against real counts is untested, because tools are rarely run side-by-side on common ground-truth data.

This paper addresses three research questions:

  1. Does the route-choice model class matter? Do dispersed and equilibrium assignment models (UE, PSL, dispersion-tolerant OD betweenness) predict observed flows better than the AoN shortest-path baseline?
  2. Does demand realism dominate algorithm sophistication? Does a real census-derived origin–destination matrix outperform a synthetic gravity model, and does the choice of demand input swamp the choice of assignment algorithm?
  3. Does a composite efficiency score change the rankings? Runtime and memory requirements vary by orders of magnitude across tools, so any honest comparison must reward accuracy per unit of computational resource — and doing so may reorder the tools relative to an accuracy-only ranking.

The benchmark presented here answers these questions with a reproducible suite (DVC pipeline, Docker image, pinned versions) and a single composite metric, the efficiency score (Equation Equation 1). Results are organised by mode — walking (Leuven), driving (Leeds) and cycling (a coverage gap) — and all tables and figures are computed live from the benchmark result files at render time.

Methods

Benchmark suite design

Results were produced by a reproducible benchmark suite, defined as a DVC pipeline (dvc.yaml) with a Dockerfile for containerised reproduction (dvc repro regenerates all stages, and dvc.lock pins the state of every stage). Each tool is run by a dedicated script in scripts/ (bench_centrality.py, bench_cityseer_od.py, bench_sdna.py, bench_flownet.py, bench_aequilibrae.py, and the demand-experiment runners run_cityseer_demand_experiments.py and run_madina_demand_experiments.py), driven by shared configuration (config/cities.yaml) and shared metrics helpers (scripts/utils/). Per-tool results are merged into per-city result tables (results/leuven_results.csv, results/leeds_results.csv), which all tables and figures in this paper read directly during rendering.

Tools

Eight tool configurations are compared: cityseer (network centrality), cityseer_demand (cityseer’s gravity demand model), cityseer_od (OD betweenness with configurable dispersion and tolerance), madina (topological betweenness and weighted betweenness), madina_worldpop (floating-catchment-area gravity with WorldPop demand), sDNA+ (hybrid centrality), flownet (path-sized logit assignment) and aequilibrae (all-or-nothing and user-equilibrium assignment).

Ground truth and demand

Ground truth comprises Leuven Telraam pedestrian counts (walk mode) (Telraam 2024) and Leeds Department for Transport annual average daily traffic (AADT) counts (drive mode) (Department for Transport 2023). Demand inputs differ by design: Leeds demand-driven tools are fed a real 2011 Census journey-to-work origin–destination matrix (pct::get_od, MSOA level; used by cityseer_od and aequilibrae), whereas a synthetic gravity demand (WorldPop residential origins × OSM-POI attractors) is used for the gravity-family tools (cityseer_demand, madina_worldpop) and for flownet, and for the Leuven OD runs. Comparing cityseer_od (real OD) with madina_worldpop (synthetic gravity) on the same Leeds network therefore isolates the effect of demand realism on otherwise comparable assignment frameworks.

Metrics and the efficiency score

Predictive performance is measured with R² against observed counts alongside runtime (compute_time_s), peak memory (peak_memory_mb) and throughput (segments_per_sec). Two R² variants are in use: linear R² (compute_metrics) for the centrality and gravity tools, and log-log R² (compute_metrics_loglog) for cityseer_od and aequilibrae, whose flows span orders of magnitude. R² values from the two variants are not directly comparable — a point we return to in Limitations. Sample sizes are small: 22 matched Telraam sensors in Leuven and 181–197 matched AADT links in Leeds (where recorded).

To combine accuracy with computational cost we use the composite efficiency score:

\[ \mathrm{efficiency\_score} = \frac{\max(R^2, 0)}{\log_{10}(1 + t) \cdot \log_{10}(1 + m)} \tag{1}\]

where \(t\) is runtime in seconds and \(m\) is peak memory in MB (Equation 1). Code complexity is quantified as lines of code (LoC, non-blank, non-comment) of each tool’s integration script plus its source code.

Leeds is modelled within a 10 km buffer clip around central Leeds (235.7k / 233.2k / 63.9k walk/cycle/drive edges), which introduces a boundary artefact for zone-based dispersion (see Limitations).

Reproducibility

The suite is designed to make every number in this paper regenerable:

  • DVC pipeline. dvc.yaml defines one stage per benchmark (e.g. bench_centrality, bench_cityseer_demand, bench_madina_gravity, bench_sdna, bench_flownet, and the Leeds equivalents bench_cityseer_od_leeds, bench_aequilibrae_leeds), plus data preparation (prepare_demand, prepare_leeds_ground_truth, generate_networks, generate_networks_leeds), the clip_leeds_inputs side-effect stage, result merging (merge_results, merge_results_leeds) and report rendering (render_report). dvc repro from the repository root regenerates every stage; dvc.lock records the hashes of all inputs and outputs.
  • Docker image. The multi-stage Dockerfile first builds the sDNA+ C++ library with OpenMP, then installs the Python/R toolchain on ghcr.io/geocompx/python (Python 3.12, Debian Bookworm) and runs dvc repro as the container command: docker build -t cenbench . && docker run cenbench.
  • Pinned versions. cityseer 4.24.1, aequilibrae 1.7.0, flownet 0.3.0 (R package), madina (fix-pandas-numpy-compat branch), sDNA+ 4.1.1 (Cross_platform branch), pandas >=3.0, Quarto 1.8.27 (pinned in the Dockerfile) and R from the base image. requirements.txt pins the Python stack; the flownet runner is scripts/run_flownet_assignment.R.
  • Random seeds. The OD sampling in scripts/bench_cityseer_od.py uses np.random.RandomState(42); all other runners are deterministic given their inputs.
  • Ground truth regeneration. Leeds AADT counts come from scripts/prepare_leeds_ground_truth.py; the census OD matrix and MSOA zones are fetched by scripts/fetch_pct_od.R via pct::get_od (MSOA geography). Leuven Telraam counts are fetched from the Telraam API.
  • The 10 km clip. scripts/clip_leeds_inputs.py applies the circular 10 km buffer clip to the Leeds networks, DfT AADT points and PCT zones/OD pairs in place (a side-effect DVC stage), so the clipped inputs are exactly the ones benchmarked.
  • Efficiency score. Defined in Equation Equation 1; the merged result CSVs carry a precomputed efficiency_score column using the same formula.
  • Rendering this paper. From the paper/ directory, with the repository virtualenv active: quarto render index.qmd --to html. All tables and figures are computed at render time from results/, so re-rendering picks up any updated benchmark outputs.

Results

All tables and figures in this section are computed live from results/leuven_results.csv and results/leeds_results.csv at render time, so they always reflect the current benchmark outputs.

Walking (Leuven, Telraam)

Table Table 2 reports, for each tool, the best-performing variant by efficiency score on Leuven walk flows.

Four findings stand out for walk flows:

  • Demand explains pedestrian counts; centrality does not. The two gravity-demand models lead on accuracy: madina_worldpop (linear R² 0.876) and cityseer_demand (0.676), both sharing the same synthetic WorldPop × POI gravity demand. The pure centrality variants of cityseer, madina and flownet explain almost none of the variance in pedestrian counts (R² 0.004–0.145), and even the best centrality-only tool (sDNA+, 0.468) trails the demand-driven models.
  • The efficiency score reorders the ranking. cityseer_od tops Table Table 2 (efficiency 3.07) despite an R² of only 0.105 (log-log), because it runs in 0.03 s versus 48.3 s for madina_worldpop — a ~1,600× runtime advantage that the score’s log-scale penalty rewards. Accuracy-only ranking would put madina_worldpop first.
  • Equilibrium helps on walk flows too. aequilibrae’s UE variants (log-log R² up to 0.155) beat its AoN baseline (0.084), though its BPR capacity model assumes vehicles and walk-mode results are therefore approximate (Limitations).
  • The evidence base is thin: only 22 Telraam sensors matched the Leuven network, so all Leuven R² values are computed on a small sample.

Driving (Leeds, DfT AADT)

Table Table 3 reports the best variant per tool by efficiency score on Leeds drive flows, and Table Table 4 zooms into the top three variants of the best tool (cityseer_od).

Five findings stand out for drive flows:

  • Demand realism beats algorithm sophistication. cityseer_od with the real census OD matrix reaches log-log R² 0.180 at 0.04 s per run — an order of magnitude better than the synthetic gravity demand (madina_worldpop, 0.022) on the same network. The gap between demand inputs (0.022 → 0.180) dwarfs any algorithm-level difference measured here (see below).
  • Dispersion beats tolerance, and both beat plain assignment. The top three cityseer_od variants (Table Table 4) all use importance-weighted centroid dispersion at 3% tolerance: R² 0.180 at a 5 km radius. Dispersion around the OD centroid outperforms zone-based k-dispersion (best k3/k5/k10 R² 0.073–0.107), and tolerance effects saturate in the 2–5% range (tol 0.03 ≈ tol 0.0 at fixed radius; tol 0.05 slightly worse).
  • User equilibrium beats all-or-nothing. aequilibrae’s UE (ue_bfw, log-log R² 0.096) beats its AoN baseline (0.083) — but AoN still wins inside aequilibrae by efficiency score, because UE costs ~1 s versus 0.12 s for roughly +0.01 R². This is exactly the accuracy–cost trade-off the efficiency score is designed to surface.
  • The 10 km clip leaves its fingerprint. Zone-based k-dispersion reverses its full-region ranking inside the clip (Leeds k3 R² 0.073 < centroid 0.180), and cityseer_od’s radius sweep (Figure Figure 1) plateaus from 8–40 km — the clip bounds the reachable network, so larger radii add nothing.
  • flownet underperforms, and its PSL variants are not yet differentiated. All six flownet beta/detour variants returned identical R² (0.0039, ~500 s each), because the runner does not yet vary the path-sized-logit hyperparameters; its potential is therefore untested by these results. sDNA+ reaches the best linear R² among the non-demand tools (0.123, MCF 200 m) but takes ~93 s and its fit is dominated by high-flow links; per-segment observed-vs-predicted plots are not yet shown because the prediction exports are not aligned with the benchmark metric path (Limitations).

Cycling (coverage gap — no per-mode sensor data yet)

Cycle-flow estimates are conspicuously absent from the tables above, and the reason is data, not tooling. Both cities’ cycle networks are already generated (data/leuven_cycle_edges.gpkg, data/leeds_cycle_edges.gpkg, produced by the generate_networks stages) and every tool in the suite can run on them, but no per-mode cycle ground truth has been integrated yet: Telraam’s Leuven sensors are used for pedestrians, DfT’s AADT points for Leeds traffic, and neither provides matched cycle counts in the current data. Closing this gap is a priority — Telraam cycle counts and DfT cycle flow data are both candidate ground truths — and the suite needs only a sensors file and a config/cities.yaml entry to add the mode.

Efficiency frontier

Figure Figure 2 plots every benchmarked variant — one point per variant — with runtime on a log x-axis and R² on the y-axis, for Leeds drive (left) and Leuven walk (right). The Pareto frontier of fast and accurate sits in the top-left: cityseer_od occupies it on both cities, combining the best fit with millisecond runtimes, while flownet anchors the opposite corner (~500 s for R² 0.004). The efficiency score is the single-number summary of this frontier: it ranks cityseer_od first in both cities precisely because it is the only tool that is both accurate and cheap.

Accuracy versus complexity

Figure Figure 3 places each tool family by its source-code size (log x-axis) and the best R² it achieves on Leeds drive flows, coloured by the efficiency score of that best variant. The headline: the cityseer family — 8.7k lines of Python (Rust core excluded) plus a ~1.4k-line integration, including a small OD-assignment script — delivers the best fit (log-log R² 0.180) at 0.04 s, while aequilibrae’s 16.2k-line codebase reaches 0.096 at ~1 s and sDNA+’s 17.2k-line C++ reaches linear R² 0.123 at ~93 s. flownet’s 1.8k lines are the cheapest to read but the most expensive to run (~500 s) for the weakest fit. Efficiency — accuracy per unit of compute — correlates with small codebases here, not large ones.

Discussion

Q1 — The route-choice model class matters, but modestly. On Leeds drive flows, dispersed and equilibrium assignment consistently beat the AoN baseline: aequilibrae UE (log-log R² 0.096) beats AoN (0.083), and cityseer_od’s dispersed centroid assignment (0.180) beats its plain shortest-path variant (0.074). Dispersion around the OD centroid matters more than the tolerance setting, which saturates in the 2–5% range. But the most sophisticated class in the suite — flownet’s path-sized logit — shows no signal yet: all six variants returned identical predictions (a runner limitation, not evidence against PSL), so the ceiling of the model-class ladder remains untested.

Q2 — Demand realism dominates algorithm sophistication. The single largest effect in the benchmark is the demand input. On Leeds, replacing synthetic gravity demand with the real census OD matrix moves log-log R² from 0.022 (madina_worldpop) to 0.180 (cityseer_od) — an eightfold improvement — while the largest algorithm-level effect measured (UE vs AoN) moves R² by only ~0.01. On Leuven walk flows, the pattern inverts in spirit: the gravity demand model explains most of the variance (linear R² 0.68–0.88) because pedestrian counts around Leuven are well predicted by population and POI attractors, and pure centrality explains almost nothing. Demand realism matters most where demand drives the model — and it matters more than the assignment algorithm everywhere.

Q3 — The efficiency score changes the rankings. An accuracy-only ranking would lead with madina_worldpop on Leuven (R² 0.876) and cityseer_od on Leeds (0.180). The efficiency score reorders both cities: cityseer_od wins Leuven too (3.07 vs 0.21 for madina_worldpop, a ~1,600× runtime gap), and inside aequilibrae the AoN variant outranks UE despite fitting worse, because UE buys +0.01 R² at ~10× the runtime. flownet drops to last place everywhere: ~500 s per run for R² 0.004. The frontier figure (Figure Figure 2) makes the trade-off visible: the top-left corner belongs to tools that are both accurate and cheap, which is the combination that matters for city-scale application.

Complexity-adjusted comparison. The complexity figure (Figure Figure 3) tempers the headline ranking. Aequilibrae’s 16.2k lines of source deliver roughly +0.01 R² over the cityseer family’s 8.7k lines at the assignment level, and cityseer’s Rust core is deliberately excluded from its Python LoC — so apparent differences in code size overstate differences in engineering effort. Whether the extra machinery is worthwhile depends on the application: production traffic models need aequilibrae’s equilibrium and matrix tools; rapid screening may not.

Mode coverage. Results are limited to walk (Leuven) and drive (Leeds); cycle flows await sensor data, with the networks and tooling already in place (Results — Cycling). Rankings are mode-dependent: madina_worldpop leads accuracy on Leuven walk but sits near the bottom on Leeds drive, which is exactly why per-mode benchmarking matters.

Limitations

  • R² metric mismatch across cities and tools: linear R² is used for Leuven Telraam walk counts and for all centrality/gravity tools, while log-log R² is used for Leeds AADT and for the cityseer_od and aequilibrae rows in both tables; R² values are therefore not directly comparable across rows, tables or cities. The metrics helpers (compute_metrics vs compute_metrics_loglog) should report both scales in future runs.
  • Single city per mode so far: walk is only benchmarked in Leuven and drive only in Leeds, so tool rankings may not generalise across urban contexts.
  • Leeds clip boundary artefact: the 10 km buffer clip around central Leeds breaks zone-based k-dispersion, reversing the k3 vs centroid ranking seen on the full region, and caps the effective dispersion radius at the clip extent (Figure Figure 1).
  • flownet is not yet exercised: its demand is synthetic everywhere, and its PSL beta/detour hyperparameters were not varied by the runner, so all six variants returned identical predictions; the path-sized-logit model class is consequently untested by these results.
  • Demand and mode approximations: aequilibrae’s walk-mode assignment is an approximation (the BPR capacity model assumes vehicles; the AoN baseline is unaffected).
  • Small sensor samples: 22 matched Telraam sensors in Leuven and 181–197 matched AADT links in Leeds (where recorded) bound the statistical power of every R² here.
  • Per-segment prediction exports are not yet aligned with the benchmark metric path: the results/*_best_predictions.csv files are produced by different code paths (interactive-map and sDNA+ runners) than the metrics in the result tables and are stale relative to the current results, so observed-vs-predicted plots are omitted from this paper until the export paths are aligned with the compute_metrics pipeline.

Conclusion

These results invite extension rather than conclusion. The three questions answered here — route-choice model class matters modestly, demand realism dominates algorithm choice, and the efficiency score reorders the ranking — each deserve more cities, more modes and more tools. Oxford is a candidate city, cycle counts are the obvious missing mode (the networks and tooling are ready), and flownet’s PSL class needs a runner that varies its hyperparameters before its model class can be judged. The suite is designed to make this cheap: a new city needs a config/cities.yaml entry, ground-truth and demand preparation scripts, and a per-tool runner — contributions to the cenbench repository are welcome.
